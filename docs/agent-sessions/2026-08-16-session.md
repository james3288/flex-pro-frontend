## Goal
- Summarize the codebase (project/intro), enumerate its features, and deep-dive the **facial-recognition login** feature and the **day-pass login** + active/inactive users loader.

## Context / Architecture (from this session)
- Frontend-only React 18 + Vite gym-membership app. Django backend lives elsewhere (base URL hardcoded in `src/others/axiosInstance.js` → `http://127.0.0.1:8000`; no `.env`).
- Login chain: `/user-login` → `UserLoginPage` → `DashboardPage` (page=PageName.USER_LOGIN) → `useDashBoard` → `MyUserLoginSection` → `FaceScannerNew3` + modals.

## Facial-recognition login (deep dive)
- Models loaded by `useFaceApiModel` from `window.location.origin + "/models"` (tinyFaceDetector, faceLandmark68Net, faceRecognitionNet, faceExpressionNet).
- `useVideoCapture` (getUserMedia 640×480); `useGetLabelFaceDescription` builds a `LabeledFaceDescriptors`; `useFaceDetectionLogic` runs every 1s and increments `loginAttempt` per consecutive match.
- `useLoginAttempt`: when `loginAttempt === 2` → `isThisYourFace=true` → `useLoginMutation.mutate()` → `useSaveTimeRecords` POSTs `/api/save_time_record/`. Already-logged-in detection uses the `1990-01-01` sentinel on `time_out`.
- Alt paths: `UserLoginIDVerificationModal` (numpad by user ID) and `StaffBypassModal` (static password `STAFFPASS` at `StaffBypassModal.jsx:4`).

## Day-pass login (deep dive)
- Separate from facial flow; no camera. `DayPassLoginModal` → select user → `getDaypassUser()` (`GET /api/get_daypass_user/`) → `setDayPassUserOnline` (`GET /api/daypass_user_online/{id}`) → `postDayPassTimeRecords` (`POST /api/daypass_time_record_insert/`) with `time_out=1990-01-01` sentinel. State in `useDayPassStore`; reset helpers in `useResetLogin.ts`.

## Data loader
- `useGetActiveAndInactiveUsers` fans out to `useGetActiveUsers`, `useGetDayPassUsers`, `getForRenewalUsers`, `useGetActiveMembership` (Promise.all), all gated behind the "Initializing user images..." spinner.

## Performance diagnosis (root causes)
1. N+1 HTTP waterfall: per user `getImagePath(id)` + `loadImageData` (HEAD+GET) + (renewal) `getExtendedSubscription` + `getExtendedTrainer`.
2. Duplicate work: `useGetActiveUsers` and `getForRenewalUsers` both fetch the same `/api/user_all_status/` and re-download the same member photos.
3. `getForRenewalUsers` runs heavy per-user extended-sub/trainer math the login screen never uses.
4. `loadImageData` HEAD+GET per image, sequential, no batching (browser caps ~6 parallel host connections).

## Proposed frontend-only fix (NOT implemented — plan only)
1. Remove `getForRenewalUsers`/`getMembershipUserActive` from the login aggregate (login only needs `activeAndInactiveUsers` + `dayPassUser`).
2. Share a single `user_all_status` response + image cache across loaders.
3. Show login UI immediately; background-load the user pool (don't block on the spinner).
4. Add a concurrency limiter for image loading.
- Backend note: an aggregated users-with-images endpoint would be the real fix (requires Django team).
